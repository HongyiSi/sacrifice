# 案例一：击杀的机会成本

**设计目标：让玩家在“现在击杀”与“暂时保留敌人”之间做出有意义的取舍。**

[返回首页](../../README.md) · [查看演示](../media/sacrifice-gameplay-demo.mp4)

## 问题与设计

如果死亡只意味着损失一个行动单位，进攻通常会集中在最快减少敌方单位数量上。我希望亡语足够强，使击杀同时带来收益和风险，但不让玩家只能回避战斗。

因此，我把三个规则放在一起：每个棋子有独立的亡语牌，死亡后仍可能影响局面；胜利既可以通过全灭达成，也可以通过四枚徽章达成；**取义在有存活队友时，获得两枚胜利徽章。**

“有存活队友”是后续迭代加入的条件。它使玩家可以通过改变击杀顺序处理风险：先处理支援者，与直接击杀取义持有者，会产生不同结果。代价是玩家需要理解存活条件与亡语结算时点，因此界面提供可查看的描述与已触发标记。

## 同一局面的两种选择

视频使用当前正式规则引擎，预设双方手牌与生命。它是规则演示，不是一场随机对局的胜率证据。对方持有的取义在这个局面中已经公开。

| 初始条件 | 分支 A：击杀取义持有者 | 分支 B：攻击另一个棋子 |
| --- | --- | --- |
| 对方已有两枚徽章 | 不变 | 不变 |
| 取义持有者只有 1 点生命 | 打击造成 1 点伤害，持有者阵亡 | 持有者保持存活 |
| 对方还有存活的队友 | 取义满足条件，增加两枚徽章 | 取义尚未触发 |
| 结果 | 对方达到四枚徽章并获胜 | 对方仍为两枚徽章，对局继续 |

录制脚本对两种结局设置了断言；结果记录在[演示时间线](../evidence/demo-timeline.json)。这个对照证明“不能立刻杀”的局面存在，**不证明每一局都会出现，也不证明每张亡语都已平衡**。

## 实现落点

规则集中在 [`rules.gd`](../../scripts/rules.gd)：`_advance_step` 安排结算，`_effects_for` 的 `sacrifice_badges` 分支在实际结算时检查存活队友，`_finish_deaths` 处理亡语后的全灭判定，避免死亡发生时过早结束对局。一次性亡语效果完成后仍保留已触发记录，供玩家回看。

演示使用 [`capture.gd`](../demo-source/capture.gd) 预设输入，调用游戏的提交、选目标和动画推进方法，没有用剪辑伪造伤害、徽章或胜负。

## 接下来如何验证

真人测试时重点记录：玩家是否能在进攻前识别风险、是否会主动获取亡语信息、改变击杀顺序是否存在可行代价，以及第一次因亡语输掉对局后能否解释原因。

如果玩家频繁觉得结局突然，应先检查信息呈现与规则解释；如果明知风险也没有可选策略，再检查牌库、费用与亡语强度。两类问题需要不同的修改。

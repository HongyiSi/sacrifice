# 案例三：把玩家反馈变成可验证的改动

**目标：减少没有决策价值的等待，并降低移动端意外中断造成的损失。**

[返回首页](../../README.md)

## 问题一：效果没有改变局面，却播放完整动画

红宝石在满血时仍然播放回复动画，蓝宝石在手牌将满时播放额外抽牌，凋萎又可能对已死亡棋子播放伤害。动画占用了时间，却没有提供对应收益，也让“有动画”与“真的生效”之间的关系变得模糊。

2026-10-21 的修改将自动触发的资格检查放到表现之前，且在每次结算时重新判断：

| 自动效果 | 跳过本次触发的情况 | 需要保留的行为 |
| --- | --- | --- |
| 红宝石 / 备用食品 | 满血、阵亡，或被保佑禁止回复 | 尚有缺失生命时仍能回复；连续效果重新检查 |
| 蓝宝石 | 阵亡、禁锢、无足够牌可摸；扣除正常摸牌后没有手牌空间 | 为正常回合摸牌预留空间；贪婪增加的正常摸牌也计入 |
| 备用物资 | 阵亡、无手牌空间、禁锢或无牌可摸 | 有一个空位时仍可获得一张；弃牌成本不撤销 |
| 凋萎的回合开始伤害 | 持有者已经死亡 | 活着时仍受伤，实际被其杀死时仍移除亡语 |
| 不死的立即复活 | 已无存活队友 | 有队友时仍按原规则复活 |
| 苦肉 | 攻击者既无法获得手牌，也不能追加出牌 | 仍有任一收益时正常触发 |
| 取义 / 遗产的自动结算 | 没有可受益的对象 | 未使用的一次性亡语保留，不标记为已触发 |

没有收益时只跳过这次自动效果，不能把整张主动牌粗暴取消。例如主动使用宝石仍可能需要转移实体牌；攻击尸体也可能触发苦肉。原来的这些交互不应因为伤害或回复为零被误删。

实现使用 [`rules.gd`](../../scripts/rules.gd) 的 `_automatic_job_has_effect`、`_gem_valid` 等判定；[`automatic_noop_test.gd`](../../tests/automatic_noop_test.gd) 覆盖两方位置、表现开关、连续触发、限制状态、卡牌保留及凋萎致死后果。详见[本次验证记录](../evidence/automatic-effects-20261021.md)。

## 问题二：手机网页崩溃后，一局测试中断

项目在 iPhone Safari 上出现过游玩一段时间后重载。仅在电脑上复现不出问题，不能说明问题已经解决，因此后续接入真机观测，并把“减少内存压力”和“中断后恢复”分开处理。

2026-10-19 的同一 iPhone、同一棋盘短窗口对照中，优先级光效从反复创建 GPU 缓冲区改为复用：持续创建约 11,178 个/秒降到 0。两个各 30 秒的窗口内，记录的内存区间分别为 662.7～786.6 MiB 与 667.3～708.6 MiB。候选版另一次静止棋盘观察持续 180 秒，没有闪退。

**这些是特定场景的观测，不是全部崩溃根因已被消除的证明。** 更长的多局操作、切后台和复杂效果仍需验证。历史记录摘要见[真机观测说明](../evidence/mobile-memory-20261019.md)。

同时，单人 AI 对局会保存规则状态、随机数状态和未确认出牌。同一设备与浏览器重新打开可恢复；最后保存或前台心跳超过 30 分钟则失效，主动退出会清除。恢复的是本地存档，不是在服务器上保留一台 AI；无法跨设备恢复。

实现入口：[`reusable_lines.gd`](../../scripts/art_ui/reusable_lines.gd)、[`ai_checkpoint.gd`](../../scripts/ai_checkpoint.gd)、[`ai_checkpoint_test.gd`](../../tests/ai_checkpoint_test.gd)。历史验证包含三场完整对局、逐步保存恢复与原局的状态对照，以及过期、损坏、退出等边界。

## 设计上的收获

先区分玩家遇到的是规则问题、表达问题还是性能问题，再确定验证方式。无效动画可以用明确的状态组合验证；偶发崩溃需要真机和长时间观测；恢复机制则必须检查“回来后是否仍是同一局”。三个问题不能用同一个“电脑上运行正常”结论概括。
